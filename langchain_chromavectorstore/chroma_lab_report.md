# Lab Report — Vector Stores with Chroma

## Topic

Storing text as **embeddings** in a vector database (Chroma) and retrieving it by
**meaning** rather than keywords. This lab covers the full lifecycle of a vector
store: create it, add documents, inspect what's stored, search it three different
ways, then update and delete entries.

## Why We Needed It

Everything earlier in this repo built toward this moment. Document loaders read
raw text, and text splitters cut it into chunks — but a pile of chunks isn't
useful on its own. Two problems remained:

**Problem 1 — ordinary search can't find by meaning.** A normal database matches
exact words. Ask it "who is a bowler?" and it finds nothing unless the word
"bowler" literally appears. It has no concept that *Bumrah* relates to *bowling*.

**Problem 2 — LLMs can't hold everything in context.** You can't paste a whole
knowledge base into a prompt. You need a way to fetch only the few most relevant
pieces for any given question.

A **vector store** solves both. It converts each piece of text into an
**embedding** — a list of numbers that captures the text's *meaning* — and stores
those vectors. At query time it embeds the question the same way and returns the
stored items whose vectors sit closest in meaning-space. This is the retrieval
engine that powers RAG: it's how a system pulls the right context to feed an LLM.

Chroma is a lightweight, local vector database that does exactly this, with the
bonus of persisting to disk so the data survives between runs.

## What Each Cell Does

**Cell 1 — Imports and environment.**
Brings in `HuggingFaceEndpointEmbeddings` (turns text into vectors),
`Chroma` (the vector store), and `Document` (LangChain's text unit), then loads
the API token from the `.env` file. Nothing runs yet — this just wires up the
tools.

**Cell 2 — Build the documents.**
Creates five `Document` objects, one per IPL player. Each has `page_content` (the
text) and `metadata` (a `team` tag). The metadata is the important design choice
here — it's what later allows filtering searches by team. The five docs are
collected into a `docs` list.

**Cell 3 — Create the vector store.**
Opens a Chroma store, handing it the embedding model as its `embedding_function`,
a `persist_directory` to save to disk, and a `collection_name`. At this point the
store is empty — this cell only sets it up. The embedding function is the heart of
it: every document and every future query will be converted to a vector by *this*
model.

**Cell 4 — Add the documents.**
`add_documents(docs)` sends each document's text to the embedding model, gets back
a vector, and stores the vector + text + metadata together. This is the first real
embedding call. It returns a list of five unique IDs — one per document — which
are needed later for updating and deleting specific entries.

**Cell 5 — Inspect the store.**
`get(include=['embeddings','documents','metadatas'])` peeks inside, returning the
IDs, the raw embedding vectors (long arrays of floats), the original text, and the
metadata. This confirms everything landed correctly and shows what an embedding
actually looks like.

**Cell 6 — Semantic search.**
`similarity_search(query='Who among these are a bowler?', k=2)` embeds the question
and returns the two closest documents by meaning. It correctly surfaces the bowler
and the all-rounder **without** the word "bowler" needing to appear as a keyword —
demonstrating that the search is meaning-based, not text-based. This is the core
feature of the whole topic.

**Cell 7 — Search with scores.**
`similarity_search_with_score(...)` returns the same results but attaches a
distance number to each. Chroma uses cosine distance, so **lower means more
similar** — the tighter match scores a smaller number. This makes the ranking
visible instead of implied.

**Cell 8 — Metadata filtering.**
`similarity_search_with_score(query="", filter={"team": "Chennai Super Kings"})`
restricts results to documents whose metadata matches the given team, ignoring the
rest. This is a hard structured filter, separate from meaning-ranking. In practice
you combine both — a real query to rank by meaning *and* a filter to scope the
pool — which is what makes vector search precise enough for real applications.

**Cell 9 — Update a document.**
`update_document(document_id=..., document=updated_doc1)` replaces one entry's text
with a longer version. Crucially, it doesn't just swap the string — it
**re-embeds** the new text, so the stored vector changes too. This keeps future
searches accurate against the updated meaning. It requires the real ID returned in
Cell 4.

**Cell 10 — Verify the update.**
Re-inspects the store. The updated document now shows the new, longer text, and its
embedding vector has different numbers than before — visible proof that updating
text also updates its meaning representation. The other four documents are
unchanged.

**Cell 11 — Delete a document.**
`delete(ids=[...])` removes one entry entirely by its ID. It takes a list, so
multiple can be removed at once. After this the store holds four documents instead
of five.

**Cell 12 — Verify the delete.**
A final inspection confirms the store is down to four documents, with the deleted
entry's ID, text, vector, and metadata all gone.

## Result

The store went cleanly through its full lifecycle:

```
create → add (5 docs) → inspect → search (plain / scored / filtered)
       → update (re-embeds) → delete → 4 docs remain
```

The semantic search returned the right players by meaning, metadata filtering
correctly scoped results to one team, and update/delete modified the store as
expected — with update confirmed to re-embed, not just replace text.
